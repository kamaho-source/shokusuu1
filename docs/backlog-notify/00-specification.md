## 1. 文書の目的

本仕様書は、CakePHP 製 shokusuu1 が **エラーおよび指定ビジネスイベントを Backlog に自動通知する**機能について、「何を満たせば完成か」を定義する。  
実装方式の細部は設計書に委ねる。

---

## 2. 背景・目的

### 2.1 背景

- 現状、アプリのエラーは主にログファイルに記録される。  
- 任意で Slack（`SlackLogEngine` / `SLACK_ERROR_WEBHOOK`）へも通知できるが、**Backlog には自動連携がない**。  
- 運用・開発の課題管理は Backlog（プロジェクト SHOKUSU）上で行うため、障害・重要イベントが Backlog に届かないと対応が遅れる。

### 2.2 目的

1. 未処理例外・致命的エラーを Backlog で検知できること  
2. テナント登録・ステータス変更など指定イベントを Backlog で把握できること  
3. API キー等を `.env` / Secrets で管理すること  
4. 通知失敗が業務処理を止めないこと  
5. 開発環境では通知を止められること  
6. Clean Architecture の依存方向（外側→内側）に従うこと  

---

## 3. 用語定義

| 用語 | 定義 |
|------|------|
| 通知 | Backlog API による **課題へのコメント追加**（既定）。設定により新規課題作成も可 |
| エラー通知 | `error` 以上の障害相当を Backlog へ送ること |
| イベント通知 | 業務上意味のある状態変化（テナント登録等）を Backlog へ送ること |
| 通知先課題 | `BACKLOG_NOTIFY_ISSUE_KEY` で指定する課題（コメント投稿先） |
| Notifier | Backlog 送信処理のアプリ内コンポーネント（Interface + 実装） |
| フェイルセーフ | 通知失敗を握りつぶし、呼び出し元の成功／失敗を変えないこと |

## 6. 機能要件

### 6.1 一覧

| 要件ID | 要件文 | 優先度 |
|--------|--------|--------|
| REQ-E01 | アプリが未処理例外または致命的エラー相当を検知したとき、Backlog 通知先課題へコメントを投稿すること | 必須 |
| REQ-E02 | エラー通知本文に、許可フィールド（ログレベル、サニタイズ済みメッセージ、発生日時、環境名。取得できる場合はファイル名・行番号・スタック冒頭）のみを含めること。送信前に機密・PII を除去／マスキングし、本文に最大長を設けること | 必須 |
| REQ-T01 | テナント登録が業務上成功した直後に、Backlog へイベント通知すること | 必須 |
| REQ-T02 | テナントステータス変更が業務上成功した直後に、Backlog へイベント通知すること | 必須 |
| REQ-G01 | イベント種別を文字列で区別できる共通通知インタフェースを持つこと | 必須 |
| REQ-C01 | `BACKLOG_API_KEY` 等の秘密情報をソースコードにハードコードしないこと | 必須 |
| REQ-C02 | `BACKLOG_NOTIFY_ENABLED` が有効でない場合、Backlog へ HTTP リクエストしないこと | 必須 |
| REQ-C03 | API キー未設定・宛先未設定のとき、アプリ起動失敗にせず通知のみスキップすること | 必須 |
| REQ-F01 | Backlog HTTP 失敗・タイムアウト時、呼び出し元の業務結果を失敗にしないこと | 必須 |
| REQ-F02 | 通知失敗のログが、再び Backlog エラー通知を無限に誘発しないこと（再帰防止） | 必須 |
| REQ-A01 | Domain/Application は Backlog HTTP 詳細に依存せず、Interface 経由で通知すること | 必須 |
| REQ-A02 | Backlog HTTP 実装は Infrastructure（または同等の外側）に置くこと | 必須 |
| REQ-S01 | 既存の Slack エラー通知と同時利用できること（置換必須ではない） | 推奨 |
| REQ-S02 | 通知本文および失敗ログにパスワード、API キー、トークン、Authorization、メール等の PII、生 SQL、内部絶対パス、リクエスト生値を含めないこと（REQ-E02 の除去規則と併用） | 必須 |

### 6.2 エラー通知の詳細（REQ-E01 / E02）

**トリガ（いずれか。重複通知防止のため入口は1系統に限定すること）**

1. CakePHP `Log` の `error` / `critical` / `alert` / `emergency`（先例: `SlackLogEngine`）を**第一候補**とする  
2. 未捕捉例外は ErrorHandler で上記 Log レベルへ集約し、Backlog へは Log 経路のみから送る（ErrorHandler から直接 Notifier を呼ばない）

**送信条件**

- `BACKLOG_NOTIFY_ENABLED=1`  
- `BACKLOG_API_KEY` あり  
- `BACKLOG_NOTIFY_MODE=comment` のとき `BACKLOG_NOTIFY_ISSUE_KEY` あり  
- `BACKLOG_NOTIFY_MODE=issue` のとき `BACKLOG_PROJECT_KEY` あり  
- ドメイン／スペースが解決できること  

**本文の除去・上限（REQ-E02 / REQ-S02）**

送信前に次を適用する:

- 許可フィールド以外を除外する  
- パスワード、API キー、トークン、`Authorization`、メールアドレス等の PII、SQL、内部絶対パス、リクエスト生値をマスキングまたは削除する  
- 本文全体の最大長: **4,000 文字**（超過は末尾を切り詰め、切り詰め明示を付ける）  
- スタック冒頭: 最大 **20 行** かつ **500 文字**  

**本文に含める項目（必須／任意）**

| 項目 | 必須 |
|------|------|
| 種別（error） | 必須 |
| ログレベル | 必須 |
| メッセージ | 必須 |
| 日時（表示は JST 推奨） | 必須 |
| 環境名（production / staging / local 等） | 必須 |
| ファイル・行 | 任意（取れる場合） |
| スタックトレース冒頭（行数または文字数上限あり） | 任意（取れる場合） |

**本文例**

```text
[ERROR] システムエラーが発生しました
環境: production
日時: 2026-07-25 21:00:00
メッセージ: ...
ファイル: path/to/File.php (行: 123)
スタックトレース（冒頭）:
...
```

### 6.3 テナント登録通知（REQ-T01）

**トリガ:** テナント登録処理が DB 反映まで成功した直後  

**本文に含める項目**

| 項目 | 必須 |
|------|------|
| 種別 `tenant_registered` | 必須 |
| テナント識別子 | 必須 |
| 登録経路（self / admin 等） | 必須 |
| 操作者（分かる場合） | 推奨 |
| 日時・環境 | 必須 |

### 6.4 テナントステータス変更通知（REQ-T02）

**トリガ:** ステータス更新が成功した直後  

**本文に含める項目**

| 項目 | 必須 |
|------|------|
| 種別 `tenant_status_changed` | 必須 |
| テナント識別子 | 必須 |
| 変更前ステータス | 必須 |
| 変更後ステータス | 必須 |
| 操作者（分かる場合） | 推奨 |
| 日時・環境 | 必須 |

### 6.5 共通インタフェース（REQ-G01）

呼び出し側は次を指定できればよい（名称は設計で確定）。

- `eventType`（文字列）  
- `title` / `body` または構造化ペイロード  
- 付加情報（配列／連想配列）  

新規イベント追加時に、Backlog HTTP 実装を複製しなくてよいこと。

## 8. 外部インタフェース

### 8.1 利用する Backlog API

| 方式 | Method | Path | 用途 |
|------|--------|------|------|
| 既定 | POST | `/api/v2/issues/{issueIdOrKey}/comments` | 通知コメント追加 |
| 任意 | POST | `/api/v2/issues` | イベントごとに新規課題作成 |

**認証**

- Backlog API キーをクエリパラメータ `apiKey` に付与する（`?apiKey=...`）。ヘッダ認証は初版対象外。  
- クライアント実装は URL／クエリ／HTTP デバッグログへ API キーを出力しないこと。やむを得ずログする場合は `***` 等へマスキングする（受入・監査要件）。  
- 例外メッセージやレスポンス本文をログする場合も、API キー文字列が含まれないことをテストで確認する。

### 8.2 アプリが公開する API

追加しない。

## 9. 設定仕様（環境変数）

| 変数名 | 必須 | 既定 | 説明 |
|--------|------|------|------|
| `BACKLOG_NOTIFY_ENABLED` | 運用上必須 | `0` | `1` のときのみ送信 |
| `BACKLOG_API_KEY` | 有効時必須 | （空） | Backlog API キー |
| `BACKLOG_DOMAIN` | 推奨 | （空） | 例 `kamaho.backlog.com` |
| `BACKLOG_SPACE_ID` | 代替可 | （空） | DOMAIN 未設定時に `{id}.backlog.com` |
| `BACKLOG_PROJECT_KEY` | `issue` モード時必須 | `SHOKUSU` | プロジェクトキー |
| `BACKLOG_NOTIFY_ISSUE_KEY` | `comment` モード時必須 | （空） | 通知先課題キー |
| `BACKLOG_NOTIFY_MODE` | 任意 | `comment` | `comment` または `issue` |
| `BACKLOG_NOTIFY_TIMEOUT` | 任意 | `3`（秒） | HTTP **全体**タイムアウト。接続 2 秒・読取 3 秒・全体 3 秒を上限とする。タイムアウト時はリトライせず失敗ログのみ（フェイルセーフ） |

設定ファイル例: `src_web/kamaho-shokusu/config/.env`（CakePHP の `export KEY=value` 形式可）。  
**Git にコミットしないこと。**

## 10. 業務ルール・制約

1. イベント通知は **業務成功後** に送る。ロールバックされた処理では送らない。  
2. エラー通知は障害確定後に送る。  
3. 通知失敗は業務成功を取り消さない（REQ-F01）。  
4. 通知失敗ログは Backlog エラー通知チャネルに再流入させない（REQ-F02）。  
5. 本文に秘密情報を載せない（REQ-S02）。  
6. 開発／ローカルは原則 `BACKLOG_NOTIFY_ENABLED=0`。  
7. Slack 通知と Backlog 通知は独立して ON/OFF できること。  
8. 同一例外の重複通知を防ぐ（イベント ID またはメッセージ指紋＋抑止窓。既定 **5 分**。窓経過後は再送可）。  

---

## 11. 非機能要件

| 区分 | 要件 |
|------|------|
| 性能 | 同期送信の全体タイムアウト上限は **3 秒**。接続 2 秒・読取 3 秒。リクエストをこれより長くブロックしない |
| 可用性 | Backlog 障害時もアプリの主要機能は継続すること |
| セキュリティ | 秘密情報は env/Secrets のみ。ログ・通知本文に API キーを出さない |
| 観測 | 通知失敗はアプリログに残す（再帰しないチャネル。生 URL／クエリ／レスポンス本文は記録しない） |
| テスト | HTTP クライアントをテストダブルに差し替えられること。失敗ログに `BACKLOG_API_KEY` 値が含まれないことを検証 |
| 互換 | PHP / CakePHP 現行バージョンで動作すること |

---

## 12. 前提・依存

- Backlog プロジェクト（SHOKUSU）と通知先課題が存在すること  
- 実行環境から Backlog API へ HTTPS で到達できること  
- 参考実装: `src/Log/Engine/SlackLogEngine.php`（エラー→外部通知の失敗握りつぶしパターン）  
- テナント登録／ステータス変更の実処理がアプリ内に存在すること（呼び出し点は設計・実装で特定）

## 13. 受け入れ条件（テスト観点付き）

| # | 条件 | 確認方法（例） |
|---|------|----------------|
| 1 | ENABLED=0 のとき Backlog にリクエストしない | モック Client の呼び出し回数 0 |
| 2 | ENABLED=1 かつ設定完備でエラー通知がコメントされる | モックが comments API を 1 回以上受ける／検証環境で課題にコメントが付く |
| 3 | テナント登録成功でイベント通知される | 同上（eventType 確認） |
| 4 | ステータス変更成功でイベント通知される | 同上 |
| 5 | Backlog が 5xx / タイムアウトでも業務 API は成功のまま | モックで例外を投げ、呼び出し元が成功を返す |
| 6 | 秘密情報がリポジトリに含まれない | `.env` が ignore、コードにキー文字列がない |
| 7 | 依存方向が Interface → Infrastructure | 静的レビュー／DI 設定確認 |
| 8 | Slack と併存できる | 両方の env を有効にしても競合で落ちない |
| 9 | 同一例外の 5 分以内の重複通知が抑止される | 同一指紋を連続送信し、comments API が 1 回のみ |
| 10 | 失敗ログに API キー生値が含まれない | モック失敗時のログ文字列を assert |
